## 与 SOLID 和系统设计原则的关系

| 原理 | 当前例子 | 边界 |
|---|---|---|
| 关注点分离、单一职责 | Breaker 管转换，Gate 管同步，Permit 管单次操作生命周期 | 是职责边界，不是类越多越好 |
| 关系显式建模 | Permit 保存哪个 Gate、哪个状态版本 | 不依赖调用方临时拼接全局状态 |
| 版本校验 | 结果提交前判断版本是否有效 | Rust 类型系统不会自动判断业务结果是否过期 |
| 所有权跟随责任 | Permit 持有 Gate 的 Arc，消费 self 报告结果 | Arc 保证对象存活，不保证结果仍有效 |
| 生命周期绑定清理 | 未完成的凭证 Drop 时处理取消 | 不等于取消远端已经执行的业务副作用 |
| 封装不变量 | 检查、占用探测机会、更新版本在同一把锁内进行 | 锁防止交错，不会自动修复 panic 中断的更新 |

直接对应 SOLID 的主要是 S（单一职责）。版本控制和 RAII 是其他设计思想，不必强行归入 SOLID 的每一项。
本例也不是完整的能力安全体系，只是用对象显式表达一次操作的授权与完成责任。

## 编译器能帮什么，不能帮什么

```text
success(self) / failure(self) + 不实现 Clone
    → 同一个凭证不能被普通代码重复提交

#[must_use]
    → 提醒调用方不要忽略凭证，不是强制保持正确作用域

Drop
    → 正常作用域退出、展开式 panic、任务取消并销毁 Future 时清理

运行时版本比较
    → 判断这次结果是否仍属于当前状态版本
```

过早 drop 仍可能导致业务统计错误；进程直接终止、abort 或刻意遗忘对象时也不能保证执行 Drop。
这是“让正确使用更容易、让错误使用更难”，不是“所有错误都被编译器消灭”。

## 可以迁移到哪些场景

```text
申请权限 → 得到凭证 → 执行操作 → 提交结果前校验 → 完成或取消清理
```

| 场景 | 类似的问题 |
|---|---|
| 页面搜索 | 旧查询返回，覆盖新查询结果 |
| 缓存刷新 | 旧刷新任务覆盖更新的数据 |
| 数据库乐观锁 | 基于旧版本的写入覆盖新版本 |
| 主节点切换 | 旧主仍试图提交操作 |

这些只是问题结构的类比，不能直接复用同一套实现。
当前 Arc 标记只在本进程内做身份比较，不等于分布式 fencing token。
分布式场景需要执行写入的一方真正拒绝旧令牌；本地忽略返回结果不能撤销远端副作用。

## 可复用的思考顺序

1. 先说运行时目标：删掉节点后，新旧请求分别应该怎样？
2. 再拆职责：谁维护可选资格，谁保障在途请求的对象存活？
3. 最后选机制：借用、Arc、锁、原子类型分别承担什么责任？

关注点分离不只发生在文件或函数拆分上，也发生在**生命周期和所有权**上。
不要看到上游使用 Arc 就照搬；先确认自己是否已经有这种运行时需求。

## 原则总表

| 第一性原理 | 当前例子 |
|---|---|
| 失败也是数据 | 使用 `Result<T, E>` |
| 阶段不同，语义不同 | Parse 与 Validation 分开 |
| 底层具体，高层统一 | 两种底层错误包装为 `ConfigLoadError` |
| 增加语义，不丢证据 | 包装原错误，而不是只保存错误字符串 |
| 所有权跟随责任 | 外层错误拥有内部错误，`source()` 只借用 |
| 机制与策略分离 | `?` 传播，`main` 决定打印或退出 |
| 机器结构与人类文字分离 | enum variant 给程序，`Display` 给人 |
| 失败尽早返回 | 解析失败后不校验，校验失败后不启动 |
| 复杂度按需求引入 | 没有共享需求就不提前使用 `Arc`、锁或 `dyn` |

## 所有权跟随责任

谁负责让数据继续存在，谁就应该拥有它：

```text
ConfigLoadError
└─ 拥有内部 serde_json::Error

错误报告器
└─ 只通过 source() 借用内部错误
```

| 场景 | 选择 |
|---|---|
| 错误要脱离原配置继续传播 | 保存 `String` |
| 只在当前调用中查看错误原因 | 返回 `&dyn Error` |
| 临时读取节点列表 | 使用 `&[Worker]` |
| 调用后仍需保留对象 | 不按值消费它 |

这也是 `DuplicateWorkerId(String)` 比借用 `&str` 更适合当前错误类型的原因：配置销毁后，错误
仍然可以独立存在。

所有权基础见[所有权、转移与借用](../concepts/ownership/move-and-partial-move.md)。

## 复杂度按真实需求引入

抽象和并发工具都有成本：

| 工具 | 只有什么时候才引入 |
|---|---|
| trait | 已经出现多个需要统一调用的实现 |
| `dyn Trait` | 需要运行时切换具体实现 |
| `Box` | 需要独占拥有动态大小值 |
| `Arc` | 确实需要多个长期所有者 |
| `Mutex` / 原子类型 | 确实存在共享可变状态或并发更新 |
| 统一错误 enum | 高层流程需要组合多种错误 |

原则：

```text
先出现问题，再引入解决该问题的抽象。
```

提前照搬上游的 `Arc`、原子变量和复杂 trait，会隐藏当前阶段真正要学习的所有权与行为边界。

## 设计选择速查

| 问题 | 推荐选择 | 原因 |
|---|---|---|
| 需要让程序区分错误种类 | error enum | 可穷举匹配 |
| 需要给用户显示错误 | `Display` | 人类可读 |
| 需要保留底层原因 | 包装原错误并实现 `source()` | 不丢证据 |
| 需要 `?` 转换错误 | 实现 `From` | 明确转换方向 |
| 错误必须独立于输入存在 | 拥有 `String` 等数据 | 不受输入生命周期限制 |
| 应用边界临时统一任意错误 | `Box<dyn Error>` | 使用方便，但类型信息被擦除 |
| 库或领域层需要精确处理 | 具体错误 enum | 保留结构化语义 |
| 测试中的固定输入必须成功 | `expect("原因")` | 失败信息清楚 |
| 用户输入可能失败 | `Result` + `?` | 不因普通输入错误 panic |

## 设计检查清单

设计一个可能失败的新流程时，依次回答：

1. 哪一步可能失败？
2. 每种失败需要保留哪些事实？
3. 哪一层最了解底层细节？
4. 哪一层需要统一调用边界？
5. 错误应该拥有数据，还是只临时借用？
6. 程序怎样分类错误，人类怎样阅读错误？
7. 是否保留了底层 source？
8. `?` 需要哪些 `From` 转换？
9. 当前抽象解决了真实问题，还是提前模仿复杂系统？
