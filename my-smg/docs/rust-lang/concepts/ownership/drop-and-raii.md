## 普通拥有值与清理

资源跟随拥有值管理：创建 String、使用、正常离开作用域时释放。move 转移释放责任；借用结束不等于拥有值销毁。实现 Drop 的类型可以执行同步清理。普通作用域清理不是 GC finalizer，也不保证强制终止进程时执行。

## 一个请求对应一个 guard

`src/worker.rs` 的节选：

```rust
pub struct InFlightGuard<'a> {
    worker: &'a Worker,
}

impl<'a> Drop for InFlightGuard<'a> {
    fn drop(&mut self) {
        self.worker.decrement_count();
    }
}
```

`begin_request` 先增加在途计数，再返回 guard。请求处理函数把它保存在 `_inflight_guard` 中；前导下划线只是表示有意不直接读这个变量，不会提前释放。

```text
begin_request → 计数 +1 → 持有 guard → 请求结束 → Drop → 计数 -1
                                      │
                         正常返回 / 错误返回 / 取消清理
```

| 写法 | 对清理的影响 |
|---|---|
| `let _inflight_guard = ...` | 保存 guard 到其作用域结束 |
| `drop(guard)` | 显式消费并销毁，立即执行清理 |
| `return` 或 `?` 提前返回 | 当前作用域中已初始化的局部资源仍会销毁 |
| Future 在暂停时仍被持有 | 存在 Future 状态里的局部资源仍活着 |
| Future 被丢弃 | 它拥有的局部状态被销毁 |

RAII 的意思是让资源的有效期跟随拥有值，而不是依靠每条业务分支手动清理。Drop 只能同步执行，不能在 drop 中直接 await；异步清理要另外显式等待。

本项目默认的进程终止和强制退出不保证执行普通作用域清理，不能把 RAII 当成进程退出时的可靠异步收尾。

## 阶段 10：先确定资源生命周期，再决定作用域

**设计 Rust 程序时，先确定资源应该覆盖哪段业务过程，再决定谁持有它、在哪个作用域释放。**
这是设计 Rust 程序的重要原则：所有权确定清理责任，作用域与 `Drop` 把责任落实到运行时行为。

这里的“资源生命周期”指资源从取得到释放的业务区间。Rust 的 `'a` 等生命周期参数表达引用的有效关系，
不会自动替你决定并发名额应该覆盖整次请求，还是仅覆盖一次上游尝试。引用约束见[生命周期](lifetimes.md)。

### 关注点分离、单一职责与生命周期分别回答什么

| 角度 | 要回答的问题 | 当前例子 |
|---|---|---|
| 关注点分离 | 哪些问题需要分别考虑？ | 请求速率、执行并发数、等待人数、节点故障分别控制 |
| 单一职责 | 一个单元承担哪项责任，因什么规则变化而修改？ | 排队容量与执行容量分别维护，调整排队规则时不混入上游重试规则 |
| 资源生命周期 | 何时取得、持有多久、何时结束？ | 并发名额覆盖整次逻辑请求，断路器凭证覆盖单次尝试 |

职责拆清楚以后，仍然要检查资源的作用域；凭证过早释放也可能编译通过，却改变业务行为。
单一职责强调围绕同一职责组织变化原因；不是一个函数只能有一行，也不是每个关注点都必须新增一个类型。

### 一次请求有不同长度的资源区间

结合 [chat](../../../../src/gateway.rs) 与[重试函数](../../../../src/gateway/retry.rs)：

| 对象或额度 | 取得位置 | 持有范围或结束方式 |
|---|---|---|
| 令牌桶额度 | 进入重试过程之前扣一次 | 不在请求结束时归还，按时间补充 |
| `Semaphore` 等待凭证 | 执行名额不足、允许排队时 | 只覆盖排队；取得执行名额后离开等待分支，或等待超时、出错、取消清理时归还 |
| `Semaphore` 并发凭证 | 通过限流后、选择节点前 | 覆盖整次逻辑请求，包括重试、退避和正文读取；销毁时归还名额 |
| 节点在途 guard | 选中节点后、进入重试前 | 覆盖该节点上的整次逻辑请求；销毁时减计数 |
| `CircuitPermit` | 每次上游尝试开始时 | 本次尝试上报结果，或取消时按凭证规则清理 |
| 注册表、策略的锁守卫 | 读取快照、更新选择状态时 | 只保护短暂的共享状态操作，在等待网络之前释放 |

```text
逻辑请求：扣一次令牌
并发名额：取得 ────────────────────────────────────── 归还
节点计数：       +1 ────────────────────────────── -1
上游尝试：             [尝试 1] ── 退避 ── [尝试 2]
断路器凭证：           取得/结束            取得/结束
```

若把并发凭证移进每次执行的重试闭包，并在尝试结束时释放，退避期间就不再占名额；
这会把限制对象从“整次逻辑请求”改成“单次尝试”。若把令牌桶扣费移进去，则每次尝试都会再次扣额度。
两者都是重复申请，但释放和补充规则不同，不能混为一谈。

把断路器凭证放在闭包内，则让每次尝试独立检查节点状态并报告结果。
位置取决于资源代表的业务区间，不能一概要求所有凭证都放在外面或里面。

### 排队与执行：同一种机制，不同的职责和生命周期

`chat` 中的 `_waiting_permit` 与 `_concurrency_permit` 都是信号量凭证，但分别表示“占一个等待位置”
和“占一个执行名额”。使用同一种 Rust 类型，并不意味着它们承担相同职责或应当同时释放。

| 凭证 | 业务职责 | 保存位置 | 正常交接或结束 |
|---|---|---|---|
| `_waiting_permit` | 限制等待执行的请求数量 | 无执行名额时进入的分支内部 | 取得执行名额后退出分支，归还等待位置 |
| `_concurrency_permit` | 限制同时执行的逻辑请求数量 | `chat` 的外层作用域 | 请求完成、错误返回、超时，或取消后 Future 被销毁时归还执行名额 |

```text
需要排队的请求：
等待凭证：取得 ── 等待执行名额 ── 释放
执行凭证：                    取得 ── 转发 / 退避 / 重试 ── 释放
                              ↑
                     先拿到执行名额，再归还等待位置
```

等待超时或出错时，返回会清理分支内的等待凭证；任务取消并销毁 Future 时，也会清理仍持有的凭证。
`abort()` 只是请求取消，等待任务结束后才能确认清理完成。
直接取得执行名额的请求不需要等待凭证；排队期间尚未选择节点，也不增加节点在途计数。

若把等待凭证一直保存到整次请求结束，正在执行的请求仍会占着等待位置，使新请求过早遇到“队列已满”。
若在请求处理结束前释放执行凭证，则还在处理的请求不再占名额，破坏整次逻辑请求的并发上限。

这个例子把三种思考连在一起：

```text
关注点分离：分别限制“等多少”和“执行多少”
    ↓
单一职责：等待规则与执行规则各自承担明确责任
    ↓
生命周期设计：让各自的凭证覆盖对应业务区间
    ↓
Rust 落实：保存到合适的作用域，销毁时由 Drop 归还名额
```

两个变量本身不能证明设计符合单一职责；还要检查规则变化是否局限在相应职责内。
这里先用独立额度和作用域表达边界，需要复用时再考虑抽取类型或函数。

### 设计时的思考顺序

1. 确定单位：一个名额代表整次请求、一次尝试，还是一次状态访问？
2. 确定区间：从哪一步开始占用，重试和等待期间是否继续占用？
3. 确定持有者：由请求 Future、单次尝试 Future，还是短代码块保存 guard？
4. 检查退出路径：成功、错误、超时，以及取消后 Future 被销毁时，资源是否按预期收尾？

`Drop` 让清理跟随拥有值销毁；拥有值何时销毁，仍取决于保存、移动和显式释放的位置。
对这里已有的 guard，命名绑定会保留它；写成 `let _ = ...` 不会保存返回的凭证。
异步清理仍需显式等待，不能仅靠 `Drop` 完成。

## 阶段 11：自定义 Drop 之后字段仍会自动销毁

对当前 `OwnedInFlightGuard`，正常销毁顺序是：

```text
销毁 guard
    |
    v
先执行自定义 Drop::drop
    +-- 在途请求计数 -1
    |
    v
再自动销毁 guard 的字段
    +-- Arc<Worker> 释放一个强引用句柄
            |
            +-- 若为最后一个强引用，销毁 Worker
```

因此 Drop 中只需要完成业务计数清理，不需要手动释放 Arc 字段；字段不能在这里随意从借用的 self 中移走。
移动 guard 会转移后续清理责任，不会在移动点执行一次 Drop 再创建一份。
Arc 的强引用计数和 Worker 的在途请求计数是两套计数，详见 [Worker 两种 guard 的对照](../../walkthroughs/worker-lifecycle.md#阶段-11拥有型-guard-独立保存节点句柄)。
Drop 实现中的生命周期声明统一见 [生命周期文章](lifetimes.md#为什么-drop-实现也出现生命周期参数)。
