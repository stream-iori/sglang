# 流式响应的内存控制与背压

[分类目录](index.md) · [总入口](../index.md) · [SSE 调度流程](../walkthroughs/sse-scheduling.md)

**流式输出减少了保存完整响应的需求；要防止内存失控，还要限制单条大小、缓冲字节、并发数量和后台生产任务。**

## 当前代码能说明什么

| 当前事实 | 能得到的结论 | 仍不能保证什么 |
|---|---|---|
| 假节点按需生成三条短事件 | 不需要积累这三条的完整历史 | 未限制整个服务的连接数，也未验证长期慢读 |
| 流内部只有编号、间隔和本次 Future，没有后台队列 | 该生成器不会把未来所有事件提前塞进无界队列 | 不能据此推断所有库缓冲、未来扩展都已有严格字节预算 |
| 网关原 `chat` 仍调用 `upstream.text().await`；新增 `chat_stream` 使用 `bytes_stream` 与 `Body::from_stream` | 前者收集完整正文；后者源码采用逐块转发路径，原理见 [SSE 逐块转发](../walkthroughs/sse-scheduling.md#阶段-11-02不收集完整响应是什么意思) | 新接口尚未在本轮编译和验收，不据此认定取消、背压或资源上限已通过 |
| 网关执行凭证当前留在 handler 局部 | 覆盖当前非流式处理过程 | 以后改成流式返回后，需要延长到正文处理结束 |

本文没有执行长期压力测试，也没有测得当前服务的每连接内存上限。

## 图一：背压怎样传递

```text
网关流式链路的设计，数据方向（可选队列尚未引入）：

上游响应 --> 读取下一块 --> 可选的有界缓冲 --> HTTP 正文 --> Socket --> 客户端

客户端读取变慢
    |
    v
网络缓冲逐渐填满，写出暂时不能推进
    |
    v
HTTP 层暂缓继续拉取正文
    |
    +-- 直接转发：暂缓读取下一块上游数据
    |
    +-- 有队列：队列填满后，生产者等待容量
                         |
                         v
                   暂缓读取下一块
```

背压允许已有缓冲暂存少量数据，不保证客户端每读一条，上游才恰好生成一条。
它也不保证远端停止计算；如果远端继续生产，可能在远端堆积，需要上游协议和服务共同约束。
Hyper 的 HTTP/1 发送流程会在不能继续缓冲正文时先推进写出，再继续拉取；这不等于整个应用已经获得固定内存上限。

## 图二：哪些地方会占内存

```text
单个流
  +-- 流状态 / Future / guard
  +-- 上游 HTTP 客户端的读取、协议缓冲
  +-- 当前正在构造的块或事件
  +-- SSE 解析、编码、拼接产生的临时空间
  +-- 可选队列中的数据
  +-- 等待入队的生产者各自持有的数据
  +-- 下游 HTTP 发送缓冲

整个服务
  +-- 所有活跃流的上述内存
  +-- 等待请求及其已解析的请求体
  +-- 连接、任务、共享状态、日志与缓存
  +-- 分配器保留空间

操作系统另有 Socket 缓冲；统计进程 RSS 时不能把它简单当成同一项。
```

预算的核心是：**每个可能积累数据的位置，都要有容量或字节上限，并覆盖离开队列后仍然存活的数据。**

## 预防措施与约束位置

| 风险 | 如何预防 | 容易遗漏的地方 |
|---|---|---|
| 把流读成完整正文 | 边读边转发，避免对无界流使用 `text`、`bytes`、`collect` 收集完整结果 | 先收集到 `Vec` 再包装成 Stream 仍然已经占满内存 |
| 单块或单条事件过大 | 限制生产时的分配和编码后大小；解析器限制未结束事件的累计字节 | 构造完几个 GB 后才检查长度，已经太晚 |
| 队列积累 | 优先直接拉取；确需解耦时使用有界 channel，发送端等待容量 | 有界 channel 限制消息条数，不限制总字节 |
| 很多生产者卡在入队 | 限制生产任务数；尽量先取得容量或字节额度，再构造数据 | 每个等待 `send` 的 Future 都可能已经持有一份大数据 |
| 入队前后数据超出预算 | 为未发送数据设置字节额度，数据真正不再占用受管内存后才归还 | 从 channel 取走只是位置变化，数据可能仍在正文或临时缓冲中 |
| 连接数过多 | 限制活跃流数量，并限制入口连接、请求体与等待数量 | 速率令牌桶不能单独限制长期存活的流 |
| 执行名额提前释放 | 让流式正文持有执行凭证和相关统计资源 | handler 返回就释放，会让实际活跃流突破上限 |
| 慢客户端长期占资源 | 设置发送停滞或无进展期限，必要时加会话期限并关闭连接 | 只设置上游读取超时覆盖不到下游堵塞 |
| 断开后生产者仍运行 | 明确取消责任、关闭队列，停止本地上游读取，回收独立任务 | 丢弃 `JoinHandle` 会让任务脱离管理继续运行 |
| 日志或缓存保存正文 | 限制日志长度、采样和缓存容量 | 主链路有界，旁路仍可能保存整份响应 |

这些是不同约束，不能互相代替。优先采用直接拉取和有限状态；出现真实解耦需求时再引入队列与字节额度。

## 有界队列为什么还不够

```text
队列容量 = 8 条

每条 1 KiB   --> 约 8 KiB 负载
每条 100 MiB --> 约 800 MiB 负载

另外还有：
多个生产者已经各自构造大块数据，正在队列外等待 send
消费者取出了数据，但还未发完
编码产生的临时副本
```

因此要联合限制：

| 限制 | 要约束什么 |
|---|---|
| 条数上限 | 排队项的数量和额外管理开销 |
| 单条分配上限 | 一次构造、解码、编码会消耗多少内存 |
| 字节总额度 | 排队、构造、发送中受管数据的总量 |
| 生产任务上限 | 队列外等待者及其状态的数量 |

如果用字节额度，申请应尽量发生在分配之前；发送后的归还位置要与真实内存拥有者匹配。
当某个库只能先返回一个块才能知道大小时，需要把允许的最大块和每个读取者可能造成的额外占用纳入预算，不能声称检查后的队列额度就是整个进程的硬上限。
`Bytes` 的切片或克隆可能共享底层分配；保留一个小切片也可能让更大的底层内存继续存活，预算不能只看切片可见长度。

## SSE 解析需要额外限制

```text
上游不断发送 data 字段，但迟迟没有事件结束空行
    |
    v
如果解析器持续拼接“当前事件”
    |
    v
即使没有完整事件入队，内存也会增长
```

| 转发方式 | 应关注的边界 |
|---|---|
| 透明转发正文块 | 不要求一块等于一条 SSE 事件；重点约束读取、缓冲及发送 |
| 解析事件后改写 | 约束行长度、未结束事件累计大小、解码与重新编码的临时空间 |

一个事件可能跨多个正文块，一个块也可能包含多条事件。内存限制要覆盖解析中的半条事件。
如果链路涉及解压缩，还要限制解压后的大小，不能仅用压缩字节数评估内存。

## 预算示例：从每条流推到整个服务

```text
M_每流 ≈ 状态 + 上游缓冲 + 当前块 + 临时编码
          + 队列负载 + 队列外待发送数据 + 下游缓冲

M_进程 ≈ 基础内存 + 活跃流数 × M_每流
          + 等待请求 + 共享数据 + 分配器额外占用
```

下面仅是预算练习，数值不是当前库默认值，也不是本项目实测：

| 假定的每流项目 | 预算 |
|---|---|
| 状态及 Future | 32 KiB |
| 上游缓冲 | 32 KiB |
| 当前构造块 | 16 KiB |
| 编码临时空间 | 32 KiB |
| 队列，8 条且每条至多 16 KiB | 128 KiB |
| 一个生产者待发送的数据 | 16 KiB |
| 下游用户态发送缓冲 | 64 KiB |
| 合计 | 320 KiB |

200 条流的这部分预算约为 62.5 MiB，还需加上基础内存、等待请求、共享数据及余量。
所有参与项有可执行的限制时，这个估算才有依据；HTTP 库、编码器的复制和超大块行为都要核对。
减少不必要的队列、同时限制活跃流，比只降低单个缓冲区通常更直接。

## 期限与取消必须能覆盖慢写

```text
上游长期不产出              --> 上游读取空闲期限
下游长期写不出              --> 写入无进展期限 / 连接层期限
整个会话占用资源太久        --> 会话期限（按业务需要）
客户端断开且本地已检测到    --> 销毁正文，取消独立生产者
```

仅把 `timeout` 放在流的下一项生成里，不保证下游堵塞时也能触发：HTTP 服务此时可能根本不再拉取流。
若要覆盖这种停滞，需要在仍受调度的连接任务或明确受管理的监控任务中执行期限和取消，并让取消确实终止相关发送、读取和生产任务。
只在尝试写入本地 Socket 时看到进展，也不等于远端应用已经消费；判断标准应明确采用哪一层的进度。
正文已经发出后，通常不能再更换 HTTP 状态码；错误策略应选择终止流或按应用协议发送错误事件，不能重放已发送内容。

## 如何验收这些预防措施

| 场景 | 构造方式 | 应观察的结果 |
|---|---|---|
| 长期慢读 | 持续输出足够多的数据，客户端限速或暂停读取，持续时间覆盖缓冲填满 | 生产速率受限，内存与队列字节在预期区间内波动，不随时间线性增长 |
| 超大事件 | 生成超过单条上限的内容 | 在过量分配前拒绝或分段；解析场景按约定终止流 |
| 未结束事件 | 持续输入字段却不发送事件结束空行 | 未结束事件累计量达到上限时停止拼接并清理 |
| 队列外积累 | 多个生产者同时等待满队列 | 生产者数和所持字节仍受限，不因队列外等待绕过预算 |
| 并发超限 | 同时保持超过上限的活跃流 | 超额请求按约定拒绝或有限等待，正文存活期间执行名额仍被占用 |
| 客户端中途断开 | 收到部分内容后关闭连接 | 本地检测后停止读取，任务退出，计数与名额恢复 |
| 下游完全不读 | 让输出量超过可用网络缓冲后继续保持连接 | 无进展期限可触发，相关资源被回收 |
| 取消后重复运行 | 多轮建立、取消连接 | 活跃任务、名额和队列回到基线，没有逐轮累积 |

三条短事件不足以填满缓冲，不能证明背压已经验收。当前案例的 `curl -N` 只能证明逐段可见；后续可用 `curl --limit-rate` 配合持续输出场景。
观测应同时包含进程内存、活跃流数、队列字节、生产任务数、读取/生成/写出进度。进程 RSS 受分配器保留影响，清理后不立即回落不能单独证明泄漏。
以上是后续教学验收设计，尚未运行这些压力场景，不据此将阶段 11 标为完成。
